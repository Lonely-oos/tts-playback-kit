# tts-playback-kit

把**任意本地 TTS 引擎**接成一条能被直播软件（OBS 等）**单独采集**的语音输出。

```
调用方 --HTTP--> [bridge 合成] --文件队列--> [可见窗口播放] <--应用音频采集-- OBS
```

- **不包含任何模型、权重、音频素材**，也不训练任何东西
- 只解决一个具体问题：**TTS 出声了，但 OBS 只能录到整个桌面**
- 自带一个"假引擎"（正弦波），不用装任何模型就能把整条链跑通

## 这不是什么

- 不是 TTS 项目。引擎由你自己提供（GPT-SoVITS、Edge-TTS、Piper、自训模型都行）
- 不是虚拟声卡方案。不需要装驱动、不改系统默认设备
- 不是实时流式合成。它是**一句话一次合成 → 排队播放**（原因见「实现原理」）

## 三分钟跑起来（不需要任何模型）

```bash
# 1) 起 bridge，用假引擎（把文字变成正弦波，音高随文字变化）
python bridge/tts_bridge.py \
  --port 8770 \
  --queue ./播放队列 --outdir ./输出 \
  --engine-cmd 'python bridge/fake_engine.py --text "{text}" --out "{out}"'

# 2) 起播放器（Windows，会弹出一个可见窗口，标题默认 TTS-PLAYER）
powershell -ExecutionPolicy Bypass -File player/player.ps1

# 3) 让它说话
curl -X POST http://127.0.0.1:8770/tts -H "Content-Type: application/json" \
     -d "{\"text\":\"你好，这是一句测试\"}"
```

窗口里会显示"正在念什么"，音频进 `./播放队列`，播完自动删。

## 实现原理

### 1. 为什么是"两段式 + 队列"，不是"一个进程直接播"

TTS 出声有两种做法：进程内直接播放（简单），或者**合成与播放分家**（本仓库）。
之所以选后者，全是 OBS 逼的：

**OBS 的「应用音频采集」抓的是进程的音频会话，而 Windows 上只有创建了窗口、
且真的在输出音频的进程，才会出现在那个列表里。**

所以必须有一个**活着的、可见的窗口**在播。而合成可能很慢（2–12 秒），
不能让它卡住播放——于是就拆成：

```
bridge（Python，管合成，可以慢）
   │  写 wav 到队列目录
   ▼
player（PowerShell + WinForms，管播放，必须有窗口）
   │  同步播放
   ▼
OBS 按窗口标题采集
```

**这条结构的关键判断是：播放器不能后台静默播。** 后台进程没有窗口，
OBS 的列表里就不会有它 —— 很多人卡在这一步，以为是"采集设置错了"。

### 2. 为什么用文件队列，而不是管道 / 内存队列 / socket

| 需求 | 文件队列 | 管道 |
|---|---|---|
| 两个进程是不同语言（Python ↔ PowerShell） | 天然可用 | 要写协议 |
| 出问题时能看"积压了几条" | `ls 队列目录` | 要加日志 |
| 崩了之后能重放 | wav 还在，直接播 | 丢了就丢了 |
| 播放失败能人工听一下 | 是 | 否 |

代价是磁盘占用（所以有 `--keep` 限制条数，配合成文件成对删除）。
文件名用 `000123_<毫秒>.wav`：**序号单调递增 → 按文件名排序就是播放顺序**，
不需要额外维护一个 index 文件。

### 3. 预热：别让第一个用户付冷启动的钱

实测（见下）**冷启动首句约 12 秒**，之后 2–3 秒。原因是模型第一次要加载进显存/内存。

所以 bridge 提供 `POST /warmup`：服务起来后立刻合成一句固定短语把模型拉热。
调用方也可以传 `--warmup` 让 bridge 启动时自己预热。

**为什么不做成"自动在第一次 /tts 时加载"**：那样第一句话的延迟会落在用户/观众身上，
而且大概率会超时。预热是一个显式的、可以失败的、可以重试的动作。

### 4. 抢占：用标记文件，不用信号

直播弹幕、语音助手被打断是常态，新的一句要盖掉旧的。

实现：`POST /tts {"preempt": true}` 写一个 `队列目录/_preempt` 标记，
播放器每轮轮询看到就**清空积压 + 停当前**。

**为什么不用信号/kill**：播放器是 PowerShell 的 GUI 进程，跨进程发信号在 Windows 上
要么不可靠（`Stop-Process` 把自己也停了），要么要额外依赖。文件标记三行代码、跨平台、还能观察。

### 5. 引擎适配：只要满足一种形态

```bash
# 命令行模板（{text} 与 {out} 会被替换）
--engine-cmd 'python engine.py --text "{text}" --out "{out}"'

# 或 HTTP 引擎（POST JSON，回音频字节或 {"out": "路径"}）
--engine-http http://127.0.0.1:9880/tts
```

bridge 不关心引擎内部是什么。它只做四件事：调引擎、校验产物、统一采样率、入队。

### 6. 采样率与格式：为什么要重采样

PowerShell 的 `System.Media.SoundPlayer` 只吃 **PCM wav**，而且对采样率挑剔
（24k/32k 有时会拒或变速）。所以 bridge 提供 `--target-sr`（默认 32000，单声道，16bit）
用 ffmpeg 转一遍；不给 ffmpeg 就保持引擎原样（接受风险）。

**为什么默认 32k 而不是 44.1k**：TTS 的输出通常 16k–32k，重采样到 44.1k 是凭空插值、
不增加信息，只增加播放端解码负担。

## 实测延迟（本机，Windows 11 + 单卡）

| 场景 | 耗时 | 说明 |
|---|---|---|
| 同语言连续合成（一句） | **2–3 秒** | 引擎已热 |
| 切换语言后第一句 | **5–6 秒** | 需要换模型（中日双模型配置） |
| 服务冷启动后第一句 | **约 12 秒** | 模型加载，必须预热 |
| bridge 自身开销 | **< 20 ms** | 起子进程 + 校验 + 入队 |
| 播放端 | 音频时长 | 同步播放，播完才取下一句 |

> 这些数字主要是**引擎**的，不是 bridge 的。换引擎要重测。

## 接你自己的引擎

```bash
# GPT-SoVITS（api.py 形态：HTTP 引擎）
python bridge/tts_bridge.py --engine-http http://127.0.0.1:9880/tts --warmup

# Edge-TTS（命令行引擎）
python bridge/tts_bridge.py \
  --engine-cmd 'edge-tts --voice zh-CN-XiaoxiaoNeural --text "{text}" --write-media "{out}"'

# Piper（命令行引擎）
python bridge/tts_bridge.py --engine-cmd 'piper --model zh_CN.onnx --output_file "{out}"'
```

> ⚠️ **`--engine-cmd` 不经过 shell（2026-11-01 起）。**
> 模板先按 shell 语法切分成参数数组，占位符只在**单个参数内部**替换，然后直接 exec。
> 所以文本里的引号、分号、`$()` 都只是普通字符，不会被执行。
> 代价：模板里**不能**用管道、重定向、`&&`。需要复杂命令行就写个脚本再调用它，
> 或者用 `--engine-http`。

## OBS 配置（三步）

1. 起 bridge + 起播放器，确认**播放器窗口是可见的**（最小化有时仍可采，但别冒险）
2. OBS → 来源 → `+` → **应用音频采集**（Windows 10 2004+ 叫「应用程序音频采集」）
3. 在窗口列表里选标题为 `TTS-PLAYER` 的那一项（或用 `-Title` 改成你认识的名字）

播放器窗口里的标题是可配置的 —— **OBS 按标题识别进程**，所以别用动态标题。

## 已知的坑

1. **后台无窗口 = OBS 采不到**（最常见）。播放器必须可见。
2. **`SoundPlayer` 只吃 PCM wav**。引擎回 mp3/ogg 要先转，用 ffmpeg。
3. **stdout 重定向会要命**：Windows 上把输出重定向到文件时，默认编码是 charmap，
   `print()` 中文直接抛 `UnicodeEncodeError` —— **服务起不来**，不是"日志难看"。
   bridge 启动时把 stdout/stderr 改成 UTF-8（失败则 replace），且 `log()` 自身不抛。
   （这条是 CI 在 Windows 上第一次跑就抓到的。）
4. **代理会拖死下载/请求**：bridge 启动时清空 `*_PROXY` 环境变量（本地服务不需要代理，
   而代理反而可能让本地请求绕出去）。
5. **抢占是"清空"不是"淡出"**：正在播的那句会被硬停（`Stop()`）。要淡出得在播放端做，
   本仓库没做——因为多数场景要的是"立刻闭嘴"。
6. **抢占只停自己启动的播放子进程**。播放器记录自己 spawn 的 ffplay PID，
   不会再用 `Get-Process ffplay | Stop-Process` 把你自己开的播放器一起杀掉。
   播放失败的产物会被移到 `输出/failed/`（不删），可以听、可以重放。
7. **队列文件名是 13 位毫秒时间戳 + 计数**，单调递增、不回绕；wav 在 txt 之后原子出现，
   所以"看到 wav"就等于"这一条已就绪"。
8. **请求体上限 64 KiB**（`--max-body`），超了返回 413。
9. **`.ps1` 必须存成「带 BOM 的 UTF-8」**。PowerShell 5.1 没有 BOM 时按 ANSI 读，
   中文全碎、字符串引号被拆开，报的却是"函数参数列表缺少 )"这类看不懂的错。
   （这条是写这个仓库时真踩到的。）
7. **队列不持久化业务语义**：wav 播完即删。要审计"说过什么"请自己记台账。
